# 06 同步设计

> 原则：**无自建服务器**。同步对象是一个加密文件 `vault.pmv`，由用户自选的网盘/同步工具搬运；本应用负责“检测外部修改 → 解密 → 三方合并 → 重新加密写回”。浏览器扩展不参与同步（它只通过桌面应用访问保险库）。

## 1. 与文件格式的关系
- 文件格式见 03 §2：头部（KDF 参数、salt、被包装的 Vault Key）+ 负载密文。负载 JSON 中与同步相关的字段：
```json
{
  "schema": 1,
  "vaultId": "8f0c…",              // 创建时生成，永不变；用于识别“同一个库”
  "revision": 1287,                 // 每次保存 +1（仅用于快速判断，合并不依赖它）
  "keyEpoch": 3,                    // 每次更换主密码 / KDF 参数 +1
  "lastWriter": { "deviceId": "win-7a1c", "at": "2026-10-05T04:30:00Z" },
  "entries": [{
    "id": "uuid", "updated": "2026-10-05T04:29:58Z", "updatedBy": "win-7a1c",
    "fieldTimes": { "password": "…", "username": "…", "uris": "…" },   // 字段级修改时间
    "passwordHistory": [{ "password": "…", "retiredAt": "…" }],
    "deleted": false, "deletedAt": null
  }],
  "settings": { "...": "...", "settingsUpdated": "…" }
}
```
- 时间统一 UTC ISO-8601；`deviceId` 为每台设备首次运行时生成的随机 ID（本地保存）。
- **更换主密码不重新加密负载**，只重新包装同一个 Vault Key。因此另一台设备即使还使用旧主密码解锁，也能用内存中的 Vault Key 直接解密新文件的负载（头部作为 AAD 一并校验）；发现 `keyEpoch` 更大时采用新头部，并提示“主密码已在其它设备更改，下次请用新密码解锁”，同时作废本机快速解锁包装（需重新启用）。
- 如果 Vault Key 本身被轮换（“重新加密保险库”操作），`keyEpoch` 增加且旧 Key 无法解密 → 提示用户输入新主密码。

- 动态码密钥默认保存在独立的 **`otp.pmv`**（08 §1），按本文同样的机制（base 副本、三方合并、墓碑、冲突副本识别、SAF）**独立同步**：拥有自己的 `vaultId`、同步位置与 `sync-state`；建议与 `vault.pmv` 放在不同网盘/目录，或选择“仅本机不同步”（例如只放手机）。两库任一同步失败互不影响。仅在不推荐的“同库存储”高级模式下，动态码项随 `vault.pmv` 的 `otpItems` 一起同步。

## 2. 本地状态
| 文件（设备本地，不同步） | 作用 |
|---|---|
| `base.pmv` | 上次成功同步后的保险库副本（加密，同一 Vault Key），作为三方合并的“共同祖先” |
| `sync-state.json` | 同步文件路径/URI、上次看到的大小、mtime、SHA-256、`revision` |
| `pairings.json`、快速解锁包装 | 与同步无关，本地专属 |
| 动态码 `clockOffset`（手动时间校准） | 设备本地，不同步（08 §6） |

## 3. 检测外部修改
- Windows：pm-win 用 `ReadDirectoryChangesW`（Rust `notify` crate）监视所在目录（含重命名，因很多同步工具先写临时文件再替换）+ 应用获得焦点/解锁时比对 (大小, mtime, SHA-256)。事件去抖 2 秒，并在文件可独占读取后再处理（同步工具可能仍在写）。
- Android：SAF 不提供变更通知 → 在应用回到前台、AutofillService 首次请求、手动下拉刷新时比对 `DocumentFile.lastModified()/length()`，必要时读取比对哈希。
- 识别网盘生成的冲突副本并自动纳入合并：
  | 工具 | 冲突文件名示例 |
  |---|---|
  | OneDrive | `vault-DESKTOP-AB12.pmv` |
  | Dropbox | `vault (张拓 的冲突副本 2026-10-05).pmv` |
  | Syncthing | `vault.sync-conflict-20261005-123000-ABCDEF.pmv` |
  | 坚果云 / 百度网盘 / Google Drive | `vault(1).pmv`、`vault_冲突_….pmv` 等 |
  规则：同目录下 `vault*.pmv` 且 `vaultId` 相同的文件均视为分支，依次与主文件合并后删除（删除前移入 `.pm-trash/` 保留 30 天）。

## 4. 保存流程（避免覆盖他人修改）
```
1. 读取磁盘上的当前文件 R（若与 sync-state 一致则跳过合并）
2. 若 R 已变化：M = merge(base, local, R)；否则 M = local
3. 写入同目录临时文件 vault.pmv.tmp-<deviceId> → FlushFileBuffers
4. 再次检查 R 是否在步骤 1 之后又变化（大小/mtime/哈希）——变化则回到 1（最多 3 次）
5. 原子替换：Windows `ReplaceFileW`（pm-win，保留 .bak）；Android 见 §7
6. base = M；更新 sync-state
```
保存后保留最近 10 个本地历史版本（`history/vault-<revision>.pmv`），用于手动回滚。

## 5. 三方合并算法
输入：`B`（base，共同祖先）、`L`（本地）、`R`（远端），均为解密后的条目映射 `id → entry`。

```
for id in keys(B) ∪ keys(L) ∪ keys(R):
    b, l, r = B.get(id), L.get(id), R.get(id)
    case:
      l == r                      → 取 l
      b 缺失, 只有 l 或只有 r      → 新增，取存在的一方
      b 缺失, l 与 r 都存在且不同  → 两端各自新建（id 为 UUID，几乎不可能相同）→ 按字段合并规则
      l == b                      → 取 r（只有远端改了，含远端删除）
      r == b                      → 取 l（只有本地改了）
      其余（双方都改了）           → fieldMerge(b, l, r)
```
`fieldMerge` 按字段逐一处理：
| 字段类型 | 规则 |
|---|---|
| 标量（标题、用户名、密码、备注、`autofillOnPageLoad`） | 只一方改 → 取该方；双方改为相同值 → 取之；双方改为不同值 → **冲突**：取 `fieldTimes` 较新者，较旧值保留（密码进入 `passwordHistory`，其它字段写入冲突记录） |
| 动态码项 `totp`（整体，`otp.pmv` 中） | 作为**一个不可分割的字段**合并（secret/算法/位数/周期必须一起生效）：只一方改 → 取该方；双方改为不同值 → 取 `fieldTimes.totp` 较新者，另一方 secret 进入 `totpHistory` 并进冲突中心 |
| HOTP `totp.counter` | 若双方 `totp` 其余部分相同，计数器取**最大值**（只增不减，避免重复使用旧码） |
| `totpHistory` | 并集，30 天后清理 |
| 集合（`uris`、`windowsApps`、`androidApps`、`tags`） | 按元素做集合三方合并：`(L−B) ∪ (R−B) ∪ (B ∩ L ∩ R)`，即双方新增都保留、任一方删除即删除 |
| `passwordHistory` | 并集，按 `retiredAt` 去重排序，保留最近 N（默认 10）条 |
| 删除 vs 修改 | 一方删除（墓碑）而另一方在删除之后修改 → **保留修改并恢复条目**，标记冲突提示“此条目在另一设备被删除” ；修改早于删除 → 删除 |
| `settings` | 各设置项按项合并，冲突取 `settingsUpdated` 较新者；`never*` 列表、`equivalentDomains` 按集合合并 |

合并结果的 `revision = max(L.rev, R.rev) + 1`，`lastWriter` 为本机。

### 5.1 墓碑（Tombstone）
- 删除条目时不立即移除，而是清空敏感字段（密码、动态码密钥、备注、密码历史与动态码历史），保留 `id`、`deleted: true`、`deletedAt`、`updatedBy`。
- 清理：`deletedAt` 超过 **90 天** 的墓碑在保存时移除。若某设备超过 90 天未同步、带回了被清理的旧条目，会把它当作“新增”恢复——可接受（宁可多一条也不丢数据），并在冲突中心标记“可能是已删除条目”。
- 回收站 UI：墓碑在 30 天内可在“最近删除”中恢复（恢复时需重新输入密码等字段，若本地历史版本中仍有则可一键恢复）。

## 6. 冲突中心 UI
- 合并后若有冲突，托盘/通知提示“同步发生 2 处冲突，已自动处理，请确认”。
- 冲突中心列出：条目、字段、本机值与另一设备值（密码以 ●●● 显示，可点按查看）、设备名、时间、自动选择的结果；操作：[保留此结果] [改用另一值] [两个都保留为两个条目]。
- 未处理的冲突不阻塞使用；30 天后自动视为已确认。

## 7. Android：通过 SAF 访问同步文件
- 实现分工：文件选择、持久授权与字节读写在 Kotlin 帮助类 `SafStorage.kt`（Qt 界面经 pm-qt → JNI 调用，AutofillService 直接调用）；解密、合并、加密在 Rust `pm-core`，Kotlin 只搬运密文字节。
- 选择文件：`ACTION_OPEN_DOCUMENT`（打开现有库）或 `ACTION_CREATE_DOCUMENT`（新建），随后 `contentResolver.takePersistableUriPermission(uri, READ|WRITE)` 持久授权；URI 存于 `sync-state.json`。
- 适用提供方：OneDrive、Google Drive、Dropbox、坚果云、Nextcloud 等 App 的文档提供者；或 Syncthing（Syncthing-Fork）同步的本地文件夹（经系统“文件”提供者）。
- 读取：`openInputStream(uri)` 全量读入内存解密；同时在应用私有目录保留缓存副本（离线时可解锁、可供 AutofillService 快速使用）。
- 写入：SAF **无原子重命名**。流程：先写私有目录临时文件并校验可解密 → `openFileDescriptor(uri, "rwt")` 截断写入 → `fsync` → 重新读取并校验哈希；失败则保留本地副本并提示重试，下次再写。
- 部分云提供者的文档提供者是“按需下载/延迟上传”：读取前调用 `DocumentsContract` 元数据判断是否为最新可能不可靠，因此每次回到前台都做一次哈希比对；写入后提示“由 xx 应用负责上传”。
- 权限丢失（提供者 App 被卸载/更新）→ 引导重新选择文件。
- AutofillService 中**只读**本地缓存副本；通过保存（onSaveRequest）产生的修改先写本地缓存，再在后台（WorkManager，约束“已解锁”时机）执行 §4 流程写回 SAF。

## 8. 同步文件夹提供方建议
| 方案 | Windows | Android | 备注 |
|---|---|---|---|
| OneDrive | 桌面客户端同步文件夹 | OneDrive App（SAF） | 关闭“文件按需”可减少延迟 |
| 坚果云（WebDAV） | 坚果云客户端 | 坚果云 App（SAF） | 国内速度好；后续可内置 WebDAV 直连 |
| 百度网盘 / 阿里云盘 | 同步空间 | App（SAF 支持程度不一） | 需实测；不支持 SAF 写入时只能手动导入导出 |
| Syncthing | Syncthing | Syncthing-Fork 本地文件夹 | 局域网/P2P，无第三方云 |
| SMB 共享 / U 盘 | 网络路径 | 不推荐 | 手动拷贝亦可（合并逻辑相同） |

## 9. 示例
**例 1：两端各改不同条目** — Windows 改了“GitHub”密码，Android 新增了“淘宝”。Android 回到前台发现远端变化：`B` 无淘宝、`L` 有淘宝、`R` 的 GitHub 密码已改 → 结果同时包含新 GitHub 密码与淘宝条目，无冲突。

**例 2：同一条目同字段冲突** — 两台设备离线时都修改了“QQ”的密码：Windows 10:00 改为 `P1`，Android 10:05 改为 `P2`。合并：取 `P2`（`fieldTimes.password` 较新），`P1` 进入 `passwordHistory`，冲突中心提示用户确认哪一个是当前有效密码。

**例 3：删除 vs 修改** — Windows 删除“旧邮箱”（09:00），Android 09:30 修改其备注 → 条目恢复并保留 Android 的修改，冲突中心提示。

**例 4：主密码在 Windows 更改** — Android 仍用旧主密码解锁（本地缓存）；同步时用内存中的 Vault Key 成功解密新文件，发现 `keyEpoch` 3 → 4，采用新头部，提示“下次请使用新主密码”，并要求重新启用指纹解锁。

**例 5：OneDrive 冲突副本** — 目录中出现 `vault-DESKTOP-AB12.pmv`，`vaultId` 相同 → 自动与主文件合并，冲突副本移入 `.pm-trash/`。

**例 6：动态码（`otp.pmv`）** — Android 上为“GitHub”动态码项导入了新的密钥（网站重置了 2FA），Windows 同时只给该项设置了置顶 → `otp.pmv` 合并后同时具有新 `totp` 与置顶状态，`vault.pmv` 不受影响；若 Windows 也在离线时导入过另一个密钥，则取较新者，另一个进入 `totpHistory` 并在冲突中心提示“请确认哪个密钥是网站当前使用的”（可分别显示当前码与网站比对）。

## 10. 测试
- 合并算法属性测试（随机生成 B/L/R 操作序列，验证：无数据丢失、交换律 merge(B,L,R) ≅ merge(B,R,L)、幂等）。
- 合并算法只在 Rust `pm-core` 中实现一次，Windows 与 Android 共用；`testvectors/merge.json` 由 `cargo test` 校验，并用 `proptest` 做属性测试。
- 故障注入：写入中断、同步工具半写文件、SAF 写入失败、时钟偏差（设备时间错乱 ±1 天时以 `updatedBy`+`revision` 辅助判定并提示）。
