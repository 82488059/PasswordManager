# 02 系统架构设计

> **技术路线（2026-10 定稿，第三版）**：Windows 桌面与 Android 共用**一个 Qt 6 应用**，界面使用 **QML / Qt Quick**；保险库/加密/匹配/TOTP/同步合并等核心逻辑**保留为 Rust 核心库 `pm-core`**，经 `cxx` 生成的类型安全 C++ 桥接层供 Qt 调用，经 UniFFI 供 Android 原生 Kotlin 组件（AutofillService）调用；Windows 自动输入/UIA/剪贴板/命名管道保留在 Rust `pm-win`；托盘、多窗口、摄像头、截屏由 Qt 提供；Android 自动填充服务、生物识别、FLAG_SECURE、SAF 为 Kotlin 原生代码（Qt 无法接管 AutofillService 生命周期）。浏览器扩展仍是独立的 TypeScript 工程。选型取舍见 §6，许可证说明见 §7。

## 2. 组件职责

| 组件 | 语言 / 形式 | 职责 | 持有敏感数据？ |
|---|---|---|---|
| **QML 界面**（`app/qml/`） | QML + JavaScript（仅界面逻辑），Windows + Android 一套 | 全部界面：解锁、列表、编辑、生成器、动态码卡片页（08 §11）、设置、配对确认、保存/更新气泡与对话框、Picker、冲突中心、迷你动态码浮窗 | 仅在“显示/编辑”时短暂持有单个字段（见 §6.4） |
| **pm-qt**（`app/src/`） | C++17/20，Qt 6 | QML 与 Rust 之间的适配层：`VaultService`、`OtpService`、`EntryListModel`、`OtpListModel`（QAbstractListModel）、`SettingsService`、`PlatformServices`（平台差异）；托盘（`QSystemTrayIcon`）、全局热键（Windows `RegisterHotKey` + `QAbstractNativeEventFilter`）、摄像头（Qt Multimedia）、截屏（`QScreen::grabWindow`）、Android JNI 调用 | 仅转发显示值；不缓存秘密 |
| **pm-core** | Rust crate | 保险库格式与加解密（Argon2id、AES-256-GCM）、双库会话（`vault.pmv`/`otp.pmv`）、条目模型、**URL 规范化与匹配（PSL）**、应用规则打分、`compare`、密码生成、**TOTP/HOTP/Steam**、otpauth / otpauth-migration 解析、二维码解码（rxing）、三方合并、扩展通道加密 | 是（明文只在 Rust 内存，`zeroize`） |
| **pm-cxx** | Rust crate（`cxx`） | 生成 Rust ↔ C++ 桥接（共享结构体、`rust::String`、`rust::Vec`、不透明句柄），只暴露句柄 + ID 风格 API | 否 |
| **pm-win** | Rust crate（`windows` crate），Windows 版链接进同一静态库 | 前台窗口与应用身份、SendInput 自动输入、UIA、受保护剪贴板、DPAPI、Windows Hello、`SetWindowDisplayAffinity`、ExtensionBridge（tokio 命名管道） | 是（自动输入直接从 pm-core 取值，不经过 C++/QML） |
| **pm-native-host.exe** | Rust 独立小程序 | stdio ↔ 命名管道转发；校验扩展 ID 与服务端签名；不解密 | 否 |
| **Android 原生模块** | Kotlin（Qt Android 包源码目录 `android/` 中） | `PmAutofillService`、AuthActivity、SaveConfirm/Pick 原生 Activity、生物识别、FLAG_SECURE、SAF、敏感剪贴板；经 UniFFI 调用 pm-core；供 C++ 经 JNI 调用 | 是（经 pm-core） |
| **浏览器扩展** | TypeScript（独立工程，不变） | 表单识别、填充、内联菜单、弹出窗口、保存提示；**不存保险库** | 仅填充瞬间的单条凭据（内存） |

**设计决策：URL 匹配、compare、TOTP、合并只在 pm-core 中实现一次**（Rust，一套测试向量）。Windows（经 C++ 桥）与 Android（经 C++ 桥与 Kotlin UniFFI）天然一致；扩展只上报浏览器提供的真实 Origin。扩展侧仅保留轻量 TypeScript 版用于 UI 展示，同样跑 url-match 向量。

## 3. 关键数据流

### 3.1 浏览器填充
1. 内容脚本识别到登录表单 → 通知 background（附字段描述，不含页面 URL 的自报值）。
2. background 从 `sender.tab.url`、`sender.frameId` 与 `sender.origin`（Chromium）/`sender.url` 取得**浏览器给出的**顶层与框架 Origin。
3. background 经加密通道发送 `match.query{topOrigin, frameOrigin}` → 桌面应用。
4. 桌面端：若锁定则弹出解锁；Core 匹配后返回条目摘要（id、标题、用户名、匹配强度、警告标记），**不含密码**。
5. 用户在内联菜单中选择条目 → `credentials.get{entryId, topOrigin, frameOrigin}` → 桌面端**再次校验匹配**后返回用户名/密码。
6. background 仅向发起请求的那个 frame 发送填充指令；内容脚本填值后丢弃引用。

### 3.2 浏览器保存/更新
内容脚本识别表单类型（登录/两步/注册/改密）并维护输入值快照，捕获提交（submit/按钮/回车/SPA 路由/POST 完成/表单消失，详见 05b §4） → background 内存暂存（按标签页，最长 5 分钟）→ `entry.compare` 由桌面端判定新建/更新 → 显示提示条（保存/更新/本站从不/忽略）→ 用户确认 → `entry.save` → 桌面端弹出（可选）确认并写入保险库 → 推送 `vault.changed` 事件。

### 3.2b Windows 原生应用与 Android 的手动保存/更新
- Windows：PasswordFieldDetector（UIA 密码框焦点）→ CredentialCaptureService 观察登录提交事件（按钮 Invoke、窗口关闭/切换）→ 读取非密码字段的用户名 → Core `compare` 判定新建/更新 → 保存/更新对话框（用户输入或粘贴密码）→ 写入保险库。不读取密码框、不安装键盘钩子（04 §7）。
- Android：onFillRequest 附加 SaveInfo → 系统保存界面 → onSaveRequest → SaveConfirmActivity 解锁后 `compare` 判定 → 保存/更新（05 §5）。
- Windows 与 Android 共用同一个 Rust Core 中的 `compare` 逻辑（扩展经桌面端调用）与 `save-compare.json` 测试向量；更新时旧密码进入 `passwordHistory`。

### 3.2c 动态码
动态码密钥默认保存在**独立的动态码库 `otp.pmv`**（独立密码、独立 Vault Key、独立锁定与同步位置），Rust Core 以两个互不依赖的 `VaultSession` 分别管理 `vault.pmv` 与 `otp.pmv`；填充动态码只需要动态码库解锁（动态码项自带匹配规则），不需要密码保险库解锁。动态码只在桌面应用 / Android 应用中由 Core 计算。浏览器扩展通过 `otp.match` / `totp.get{otpId, topOrigin, frameOrigin}` 请求，桌面端复核 Origin 后只返回 `{code, remaining}`，扩展从不接触密钥。Windows Auto-Type 的 `{TOTP}`、Android 的 OTP 数据集同样在填充瞬间计算（详见 08）。

### 3.3 桌面自动输入与扩展的协同
前台窗口为已连接扩展的浏览器时，全局热键转发为 `fill.trigger` 事件给该扩展（填充当前活动标签页），而不是 SendInput 盲打，从而获得精确的 Origin 校验。若扩展未连接，回退 UIA 读取地址栏 + SendInput，并在 UI 中标注“未经扩展校验的网址”。

### 3.4 Android 浏览器填充
系统回调 `onFillRequest` → 遍历 AssistStructure 找到 `webDomain` 节点 → 校验请求方包名在“可信浏览器白名单”且签名匹配 → Core 匹配网站条目 → 返回需认证的数据集 → 用户解锁后填充。详见 05。

## 4. 进程与生命周期
- **Windows**：单实例 Qt 进程（`QLocalServer` 或命名互斥体检测；第二个实例把参数转交后退出）；`QApplication::setQuitOnLastWindowClosed(false)`，关闭主窗口即最小化到托盘。pm-win 的 ExtensionBridge、WinEvent/UIA 监听运行在 Rust 后台线程（tokio 运行时 + 专用 UIA MTA 线程），事件经 pm-cxx 回调投递到 Qt 主线程（`QMetaObject::invokeMethod(..., Qt::QueuedConnection)`），再以信号通知 QML。
- 浏览器按需启动 pm-native-host（`runtime.connectNative`），连接断开即退出；一个浏览器 profile 一个长连接。
- MV3 Chromium 的 Service Worker 可能被回收：活跃的 Native Messaging 端口会保活 SW；被回收后重连并重新握手（< 50 ms）。
- 桌面应用未运行时：NativeHost 可按设置尝试启动桌面应用（启动参数 `--background` 只进托盘），否则返回 `APP_NOT_RUNNING`。
- **Android**：QtActivity（QML 界面）与 AutofillService 在同一进程；`libpm_core.so` 为进程单例，UI 中解锁后自动填充可在超时前直接使用解锁状态（反之亦然）。系统单独拉起 AutofillService 时**不加载 Qt**（只加载 `libpm_core.so`），冷启动快、内存小。自动填充流程中的界面（认证、保存/更新确认、搜索选择）为**原生 Kotlin Activity**，原因：Qt for Android 以单个 QtActivity 承载 QML，难以作为可返回结果（`setResult` + `EXTRA_AUTHENTICATION_RESULT`）的独立 Activity 被系统多次拉起，详见 05 §0。

## 6. 关键选型

### 6.1 为什么选 Qt 6 + QML
| 维度 | 说明 |
|---|---|
| 一套界面覆盖 Windows + Android | QML 声明式界面 + Qt Quick Controls，布局按窗口宽度自适应 |
| 桌面多窗口 | **原生支持**：Picker、保存气泡、迷你动态码浮窗都是独立 `Window`，可设 `Qt.Tool`、`Qt.WindowStaysOnTopHint`、`Qt.WindowDoesNotAcceptFocus`、`Qt.FramelessWindowHint` 等标志组合，解决了 Flutter 方案中多窗口不成熟的问题 |
| 托盘 | `QSystemTrayIcon` 内置（QML 侧可用 Qt Labs `SystemTrayIcon` 或 C++ 封装） |
| 摄像头 / 截屏 | Qt Multimedia（Windows 与 Android 一套 API）、`QScreen::grabWindow` |
| 代价 | Android 集成需要 JNI 与 Kotlin 原生 Activity；自动填充相关界面需原生实现（少量重复）；许可证需注意（§7）；Qt for Android 构建链与 APK 体积（约 +15–25 MB/ABI） |

### 6.2 核心库：保留 Rust 还是改为 C++
**结论：保留 Rust `pm-core`**，C++ 只做 Qt 适配层。

| 维度 | C++ 核心（与 Qt 同语言） | Rust 核心 + cxx（选用） |
|---|---|---|
| 与 Qt 的集成 | 最直接，无桥接层 | 需要 `pm-cxx` 桥接 + Corrosion 构建；QObject 仍用 C++ 写 |
| Android AutofillService（Kotlin） | 需手写 JNI 绑定（易错、样板多） | UniFFI 自动生成 Kotlin 绑定 |
| 密码学依赖 | Qt 不提供 Argon2id/AES-GCM，需引入 OpenSSL 3 或 libsodium（多平台构建与许可证管理） | RustCrypto 纯 Rust crate，跨平台构建简单 |
| 内存安全 | 解析不可信输入（otpauth、protobuf、二维码、vault 文件、扩展消息）在 C++ 中风险更高 | 内存安全；`zeroize` 清零 |
| 已有设计与测试向量 | 需重写 | 不变（上一版已以 Rust 为核心） |
| 团队技能 | 只需 C++/Qt | C++/Qt + Rust |

决定性理由：AutofillService 的 Kotlin 绑定、密码学依赖与内存安全。若团队完全没有 Rust 能力，可退而采用“C++ 核心 + libsodium/OpenSSL + 手写 JNI”，但需重新评估 03 中的内存与解析安全措施。

### 6.3 Rust ↔ Qt 桥接方式
| 方案 | 说明 | 选择 |
|---|---|---|
| C ABI（`extern "C"` + 手写头文件） | 最简单，但类型不安全、所有权易出错 | 否 |
| **`cxx`** | 类型安全的 Rust/C++ 互调，共享结构体、`rust::Box`、`UniquePtr`；QObject 在 C++ 中以惯用方式编写 | **是** |
| KDAB `cxx-qt` | 可直接用 Rust 定义 QObject/属性/信号 | 备选：功能强，但增加构建与学习复杂度，且会让 Qt 类型渗入核心 crate；v1 不采用 |

### 6.4 跨语言边界原则
- 明文秘密**默认不出 Rust**：自动输入（pm-win）、剪贴板写入、浏览器 `credentials.get` 响应、Android 数据集都在原生侧直接从 pm-core 取值。
- C++/QML 只在用户主动“显示密码 / 编辑条目 / 查看动态码”时取得单个字段：C++ 侧用 `QByteArray` 持有并在用完后 `secureZero`（`SecureZeroMemory` / `explicit_bzero`）；进入 QML 后成为 `QString`（隐式共享，无法保证清零）——这是已知限制，UI 通过按需获取、离开页面即清空属性、`TextField.echoMode: TextInput.Password`、不写日志来降低残留（03 §3）。
- 动态码卡片每秒刷新只取“当前码 + 剩余秒数”；锁定事件由 Rust 回调 → C++ 信号 → QML 立即清空模型。
- 接口以“句柄 + ID”设计（`VaultHandle`、`entryId`、`otpId`），不传整库 JSON；列表模型只拉取摘要字段。

## 7. 许可证说明（Qt）
> 以下为工程层面的说明，不构成法律意见；发布前应由项目负责人确认。
- Qt 6 以 **开源许可（LGPLv3，部分模块仅 GPLv3）** 与 **商业许可** 双许可发布。本项目使用的模块（Qt Core、Gui、Qml、Quick、Quick Controls、Quick Shapes、Svg、Multimedia、Network）以 LGPLv3 提供；**不使用**仅 GPLv3/商业提供的附加模块（如 Qt Charts、Qt Virtual Keyboard、Qt Quick 3D 等），避免把整个应用拉入 GPL。
- 采用 LGPLv3 时的主要义务：
  - **动态链接** Qt（Windows 随附 Qt DLL；Android APK 中为 Qt `.so`），不做静态链接（静态链接需额外提供可重新链接的目标文件）；
  - 随软件提供 LGPLv3 许可证文本与 Qt 版权声明，在“关于”页列出所用 Qt 版本与模块；
  - 若修改了 Qt 本身，需公开对 Qt 的修改；
